# 收杆 QTE 的形态分类报告（A / B / C 三类）

> 数据：`~/.fishprobe` 全量采集（123 个事件文件，**119 局**，未按"能否解出几何"过滤）
> 工具：`app/_probe_formB.py`（全量分类）、`_probe_formBC.py`（帧结构）、`_probe_green.py`（像素色段）、
> `_probe_verifyC.py`（C 类验证）、`_probe_alignC.py`（按键对齐）
> 日期：2026-10-15　状态：**形态划分【实测】；B/C 的玩法由用户确认**

---

## 1. 为什么要重扫

v0.2.0 的几何层是在"**解得出几何的局**"上做的，而 `qtemap.qte_episodes()` 里有一句
`if len(gs) >= 5` —— **只保留解得出几何的局**。所有离线验证与 QA 交叉检查都走这条路，
于是**筛选条件本身把另一批局排除在外**，才有了"上机后 39% 帧解不出"的意外。

不筛几何重扫 119 局 → 形态是**三类**，不是两类：

| 形态 | 帧结构（subtitle） | 局数 | 占比 | 有独立绿区 | 有指针 |
|---|---|---|---|---|---|
| **A** | `B00C(bar10) \| 绿区 B012/13/14 \| B001(pointer)` | **71** | 60% | ✅ | ✅ |
| **C** | `B00x(bar1..bar9/rainbow) \| B001(pointer)` | **24** | 20% | ❌ | ✅ |
| **B** | `B011(bar11) \| B00D..B010(鱼图标)` | **24** | 20% | ❌ | ❌ |

**【实测】关键性质：形态按局固定。** 每局内段数恒定（从无混合），所以"某局全帧 geom_ok=false"
不是噪声、不是抽帧，而是**那一整局就是另一种玩法**。

## 2. 三类形态的细节

### A 类（71 局）—— 已解出，v0.2.0 的几何层就是为它做的

- 首段**恒为** `B00C` = `bar10.png`（5262 帧无一例外）
- 中段 `B012/B013/B014` = `judgment_area_easy/normal/hard.png`（**45/36/27px 纯绿**）
- 末段 `B001` = `pointer.png`（5×15 白条）
- 开局标题 = **`按下 左键 开始` / `按下 左Shift 开始`**
- 玩法：**点按**（指针进绿区时按键）—— 与既有几何模型一致

### C 类（24 局）—— 需要**按住**（用户确认）

- 首段 = `B00x` 之一（**局内恒定、局间变化**），映射到 `bar1..bar9 / bar_rainbow`
  - 实测分布：rainbow 6、bar6 4、bar8 4、bar9 3、bar3 2、bar4 2、bar2 1、bar7 1、bar5 1
- 末段 `B001` = pointer，**逐帧移动 +2~+5px/tick**（有回扫）
- **没有绿区字形** —— 判定区不在文本里，在**底图的图案**上
- 开局标题 = 提示语，**没有「按下 X 开始」**：
  `鱼上钩了，集中注意力！`(2) · `不要松懈，鱼正在挣扎！`(5) · `距离收竿只差一步！`(6) ·
  `好机会，保持冷静！`(3) · `抓紧竿子，鱼就在钩上！`(1) · `稳住，胜利就在眼前！`(1) ·
  **`绿色!` / `紫色!` / `红色!`（各 2 局，全落在 rainbow 底图上）**
- **用户确认玩法**：这类局 **需要按住某个键**；`绿色!/紫色!/红色!` 是**题目 —— 指针到该颜色时按键**

### B 类（24 局）—— 无指针、无操作要求

- 首段**恒为** `B011` = `bar11.png`（256×**20**，teal 长条 + 一列黑白棋盘格游标）
- 次段 `B00D..B010` = `fish_icon.png` / `struggling_fish_icon.png`（鱼 / 挣扎的鱼）
- **title 在逐帧递增**：`B011→B012→B013→B014→B015→B016→B017…`（约 50–100ms 一跳）
- 局时最长（55–235 帧），**帧里没有指针、没有绿区**

## 3. 一个必须记住的陷阱：`icons.json` 与 `default.json` **码点重叠**

`服务器材质10.2.zip` 里有**三张** `customfishing` 字体表：

| 字体 | 码点 | 映射到 |
|---|---|---|
| `customfishing:default` | B001..B014 | `bars/*.png`（pointer / bar1-11 / fish / judgment_area） |
| **`customfishing:icons`** | **B001..B009** + **B011..B019** | `icons/progress_1..9.png` + `icons/strain_1..9.png`（各 26×26） |
| `customfishing:offset_chars` | F801..F808, F811..F818 | `base/space_split.png`（带符号位偏移） |

**同一码点在两个字体里含义完全不同**：`B001` 在 default 是"指针"，在 icons 是"进度图标 1"；
`B005` 在 default 是 `bar4.png`（256 宽），在 icons 是 `progress_5.png`（26 宽）。

⇒ **解码一帧前必须先确定这段文本用的是哪个字体**（由服务端文本组件指定），
否则宽度整片错位。**这是 B 类 title 递增现象的解释**：title 用的是 `customfishing:icons`，
`B011..B019` 正是 **strain_1..9 = 挣扎动画的 9 帧**。

**【实测】判据**：帧里出现 `B00A/B00B/B00C`（bar9/rainbow/bar10）或 `B00D..B010`（鱼图标）
或 `B012..B014`（绿区）→ 只能是 default 字体（icons 未定义这些码点）。

## 5. 底图的水平对齐：定为「内容贴 cell 右缘」

**【实测】A 类全量统计**（71 局）：
- `zone_x` 范围 **85 .. 222**（中位 152）
- 指针 x 范围 **64 .. 236**（起点中位 73、终点中位 177）

**判据（决定性）**：A 类的底图是 `bar10`，其**可见内容只有 0..162**。
若内容**左对齐**（条 = 0..162），则 `zone_x = 222` 会落在条的**透明区**上 —— 玩家根本看不见绿区，
游戏不可能这么设计；而 `zone_x` 实测能到 222（占 87% 的条宽位置）。

若内容**贴 cell 右缘**（条 = 94..256）：
- `zone_x` 85..222 → **全部落在条内** ✓（85 与 94 差 9px，在 ±4.5px 量化残差量级附近）
- rainbow 局的六段（图内 4..115）→ 映射到屏幕 **141..252**，**正好覆盖指针 129~246** ✓
- bar6 局（内容 0..183）→ 条 = 73..256，指针 64..132 **基本落在条内** ✓
- bar11（内容 0..221）→ 条 = 35..256

**⇒ 结论：底图 glyph 的可见内容贴在 advance 空间的右缘。**
（机制未查——可能是资源包 font json 的写法或 provider 的绘制行为；但三种数据一致支持该结论。）

**实现含义**：任何要用"底图上的彩色段位置"做判定的逻辑（即 C 类），
必须加上偏移 **`条左端 = 256 − 图内容宽`**，直接把图内坐标当屏幕坐标会整体偏左 90~140px。

## 6. 对 fishauto 的直接结论

1. **不要在 B/C 形态上开 geometry** —— 当前实现遇到解不出几何的帧会 `geom_skip` 且**不按**，
   而 B/C 占 **40%** 的局，切过去就是"四成的局一次都不按"。
2. **但 cadence 也不是答案** —— 玩家在 B/C 局**并不连按**（C 类实测局内零按键），
   连按属于"瞎按"，既不解决问题也可能误触。
3. **fishauto 目前缺一个能力：长按**。C 类需要**按住**（用户确认），
   现有 `Presser` 的 `hold_ticks`（默认 2 tick = 100ms）是为 Shift 的短暂按-松设计的，
   **不足以表达"整局按住"**。
4. **最该先做的一步（小改动、收益大）**：让 `geom_skip` 时**不摆烂**——
   按形态分流：`A → geometry`、`C → 长按（或按题目颜色）`、`B → 什么也不做`。
   形态判据极简单：**看帧里有没有 `B001`（指针）和 `B012..B014`（绿区）**。
