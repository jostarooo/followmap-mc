## 1. 提醒方式选型：为什么是「水滴音 + 闪任务栏 + 打点」（抖动可选）

需求把方案限定在「水滴音」和「屏幕抖动」之间。结论是**水滴音当主通道，抖动改成抖地图窗口，
且默认关掉**（理由见 1.1）。

| 通道 | 保留 | 理由 |
|---|---|---|
| **水滴音** | ✅ 主通道 | 骑鞘翅时眼睛盯的是**全屏游戏画面**，第二屏地图只是余光扫到。**只有声音是 100% 有效**的——不看地图也能听见。三种遗迹用三个音高，光听声音就知道是哪一种。 |
| **屏幕抖动** | ⚠️ 改为「抖动地图窗口」 | 抖动**整个屏幕**需要注入游戏进程或改显示设置，Python 层没有正当手段做，硬做也会干扰操作。改成抖地图窗口：醒目、零侵入，且与地图的视觉指向一致（声音把你叫过来，抖动告诉你「看这里」）。用 Tk `after` 链驱动，不阻塞主循环。 |
| **任务栏闪烁** | ✅ 补充 | `FlashWindowEx` + `FLASHW_TIMERNOFG`：**不抢焦点、不打断游戏**，切回桌面时一眼看到是哪个窗口在报警。 |
| **地图永久打点** | ✅ 补充 | 图标 + 名字留在图上，事后可回看。 |

音效**现场合成**（`alerts.py: synth_drop`），不依赖任何外部音频文件。水滴声的物理来源是
气泡振荡，频率**上滑**（不是下滑——下滑的正弦听起来像敲门/报警，不像水），
配指数衰减包络 + 二次谐波。实测产物：`drop_high` 56KB / `drop_mid` 60KB / `drop_low` 66KB
（三连响后的完整波形）。

### 1.1 实测后的两处调整（用户报的需求）

使用场景是**笔记本自带屏挂机飞末地跑图 + 外接大屏刷视频**，程序的目的就是「看视频也别错过遗迹」。

1. **默认只出声，不抖窗口**。默认模式 `auto` 的通道是 **水滴音 + 任务栏闪烁 + 地图打点**，
   **不抖地图窗口**——眼睛根本不在笔记本屏上，抖了也看不见，反而白耗一次重绘。
   要抖动用 `--ruin-alert both`。
2. **音量提高 + 连响 3 下**。波形峰值先归一化到满刻度，再让增益 > 1 走 `tanh` 软削波——
   峰值恒定不变（不会数字破音），削波把**能量**推上去，听感更"顶"。
   再叠 3 连响（间隔 170ms），才穿得过外放视频声。默认 `--ruin-volume 1.5`，
   实测穿视频声用 1.5~2.0。

| 模式 | 通道 |
|---|---|
| **`auto`（默认）** | 水滴音 + 任务栏闪烁 + 打点 |
| `sound` | 只出声 |
| `both` | 水滴音 + 任务栏闪烁 + **窗口抖动** |
| `shake` / `flag` / `off` | 只抖 / 只闪 / 关闭 |

**可用 `--ruin-alert` 指定，运行中按 `r` 循环**（`auto → sound → both → flag → off`）。
另有 `--ruin-volume`（0.2~3.0）、`--ruin-repeat`（连响几下）、`--no-ruin`（整体关掉）。

> **关于日志里的「任务栏闪烁 未生效」**：`flash()` 需要窗口句柄，`--selftest`
> 这类**无窗口**运行传进来的是 `None`，于是被判为未生效——这是预期行为，不是故障。
> 实测在真正开窗口的运行里三通道全绿：
> `10-09 00:12:20  发现 巫师的圣修所 (48661,29686) 纯度94% -> 水滴音+窗口抖动+任务栏闪烁`。

## 2. 触发时机：为什么「新落盘的区块」等价于「新加载的区块」

模组只在**玩家真正加载了**的区块上写 `.bin` 文件。所以「文件是新出现的」天然等价于
「这块地形刚进视距」——正好是需求要的语义，而且**天然合规**：只读已经落盘的数据，
绝不扫视距外、不做任何自动化操作。

副作用是好的：`RuinWatcher` 只处理 `index_<维度>.json` 里 **region 版本号变大**的目录，
所以**每轮耗时只与玩家实际跑了多少成正比**，跟已探索面积无关。

## 3. 标定过程：阈值不是拍的

### 3.1 数据源

`structures_DIM1.json`：对末地 1484 个 region 全量扫描出的 **1274 个人造结构候选簇**。

> ⚠️ 一个关键发现：该文件每个簇的 `blocks` **只存了前 10 项**（`len=10` 而 `count=2225`）。
> 所以用它算出来的「纯度」会被**系统性高估**——A 段只能当近似参考，**真实纯度必须以
> 完整窗口为准**（B / C / D 段）。这条是踩出来的：A 段显示某巫师纯度 0.84，真实窗口只有 0.744。

### 3.2 真值怎么定（与分类器解耦）

真值 = **余弦相似度**（参考向量取文档记录的真实实例实测方块数，余弦 ≥ 0.90 才算真值）。
用余弦而不是「模板阈值」当真是为了避免「用同一套标准互相证明」。

真值：白金 13 处 / 武士 59 处 / 巫师 57 处，合计 129 处（占 1274 的 10.1%）。

### 3.3 纯度阈值定标

补全用料表 + 家族锚点**之后**重跑（真值 13/59/57，1274 个候选簇）：

| min_purity | red_wool | 白金星殿 | 武士的修行地 | 巫师的圣修所 | 同类非典型 | 类型混淆 |
|---|---|---|---|---|---|---|
| 0.72 | 5 | 12/13 | 58/59 | 55/57 | 46 | **0** |
| 0.72 | **3** | **13/13** | 58/59 | 55/57 | 46 | **0** |
| 0.76 | 3 | 13/13 | 58/59 | 55/57 | 46 | 0 |
| **0.80** | **3** | **13/13** | **58/59** | **55/57** | **46** | **0** ← 采用 |
| 0.84 | 3 | 13/13 | 58/59 | 55/57 | 45 | 0 |
| 0.86 | 3 | 13/13 | 58/59 | 55/57 | 45 | 0 |
| 0.90 | 3 | 13/13 | 58/59 | 55/57 | 44 | 0 |

**七档召回完全相同、混淆全程 0** —— 说明三类的区分**靠的是硬特征本身**，
不是纯度阈值在"卡"。阈值只负责「别把小遗迹算进来」，调它基本不影响召回。

> ⚠️ 早期版本（**补家族锚点之前**）的表不是这样：那时 0.86 会让巫师召回掉到 46/57=80.7%，
> 所以曾据此写下"0.86 过严"。**那条结论已作废**——现在的瓶颈在锚点表达力，不在阈值。

白金 `red_wool` 锚点由 5 降到 3：有一处真实星殿只有 4 个红羊毛，5 会漏掉。
**注意 red_wool=5 那一行白金恒为 12/13**——这就是漏检的那一处（与纯度阈值无关）。

### 3.4 补全「用料表」（真实数据发现的漏检）

模组每 chunk 只存**每列的地表方块**，同一座建筑被屋顶/上层挡住的部分，露出来的方块比例会变。
用真机数据核对后发现两类问题：

1. **用料表缺项 → 纯度虚低**。巫师圣修所窗口里 25.6% 的人造方块不在原表内——
   灵魂土 258、泥 58、下界芽 39、玄武岩 34、平滑玄武岩 34、蛛网 14、铁砧 2……
   这些**本来就是这座建筑的用料**（灵魂主题 + 工匠台），只是原表没列。
   补全后巫师纯度从 0.744 → **1.00**。
2. **同一建筑存在工艺变体 → 固定阈值会漏**。实测一处分金星殿用
   `mossy_cobblestone_stairs` 92 个，另一处只用 `mossy_stone_brick_stairs` 22 个。
   因此给指纹表加了 **`any`「至少满足一组」的锚点组**：

   ```json
   "any": [
     {"minecraft:mossy_cobblestone_stairs": 15},
     {"minecraft:mossy_stone_brick_stairs": 12},
     {"minecraft:smooth_stone_slab": 10, "minecraft:smooth_quartz_stairs": 10}
   ]
   ```

   加之前：真机数据只认出 10 处（全是巫师，**白金全漏**）。加之后：认出 **14 处**，
   两种变体的白金都抓到了。

### 3.5 方块家族（groups）：用户实测报的「武士漏检」

**现象**：用户截图反馈「旁边的武士遗迹没有检测出来，上一个巫师遗迹正常提醒」。
用真机数据复现，确认武士**一处都没命中**。

**根因**：指纹表把武士的硬特征锚死在**单个方块名**上——`end_stone_bricks ≥ 90`。
但同一座武士修行地的「末地石砖系」构件，在**不同实例之间分布会漂移**：
真实几处分别是 `end_stone_bricks` 15 / `end_stone_brick_wall` 38 / `end_stone_brick_stairs` 11，
`end_stone_bricks` 单项**永远到不了 90**——可三项合计却稳定在 **64~67**。
锚点钉单项 ⇒ 判据自相矛盾 ⇒ 全漏。

**修法**：给指纹表引入 **`blocks` 家族（groups）** 概念——把「同一种建筑构件的不同形态」
归成一个家族，锚点写在**家族合计**上：

```json
"groups": {
  "end_brick": ["minecraft:end_stone_bricks",
                "minecraft:end_stone_brick_wall",
                "minecraft:end_stone_brick_stairs",
                "minecraft:end_stone_brick_slab"]
},
"anchors": {"netherrack": 60, "@end_brick": 45, "polished_basalt": 8, "@crimson": 25}
```

`@end_brick` 即家族合计。**家族存在的理由**：建筑的"用料表"是稳定的，但
「同一种料以哪个形态露在地表」是漂移的——只有**合计**才是那个稳定的量。
同轮还给巫师加了 `@netherrack` / `@blackstone`、给白金加了 `@stone_brick` / `@mossy`。

**效果**：真机命中从 **0 → 6 个武士**（纯度 0.86~0.92，独立余弦 0.56~0.69 也归到同一类）。
这条判据同时被固化成 **E 段回归用例**——防止以后有人改指纹表时"顺手"把锚点又钉回单项。

### 3.6 地形淹没：为什么"绝对计数当锚点"必然漏（本轮）

**现象**：用户又报「这个巫师没有检测出来」（附图）。放大观察，能看到巫师遗迹的斜向长横梁与
深色砖体，但**明显被浅色地形方块（`end_stone`）吃掉一大块**，只剩零散露头。

**根因（一条机制，不是一处 case）**：本服遗迹**直接刷新在地形上**，有概率被地形方块覆盖。
被淹没的某一列，其「地表方块」就成了 `end_stone`——而 `end_stone` 属于 `NATURAL`，
**不计入直方图**。于是这一整座建筑的所有用料计数，被**等比缩小了 s 倍**（s = 露出比例）。

由此推出三条推论，它们决定了一切：

| 量 | 淹没后（等比缩 s 倍） | 能否当锚点 |
|---|---|---|
| **纯度** = 该类用料 / 窗口内全部人造方块 | **不变** | ✅ 本来就不受影响 |
| **占比** = 主料 / 该类用料总量 | **不变** | ✅ **尺度无关 → 抗淹没的关键** |
| **绝对计数** = 某方块出现次数 | **× s** | ❌ 缩到阈值以下就漏 |

**所以：「拿绝对数当锚点」的判据，淹没到一定程度必然漏**——这不是阈值调高调低的问题，
是判据形式本身的缺陷。

**修法（两条一起上）**：

1. **新增「占比锚点」`ratios`**。`"minecraft:xxx": 0.26` 表示「该方块 / 该类用料总量 ≥ 0.26」。
   尺度无关，是抗淹没的核心。实测巫师主料占比：真值窗口 0.31~0.38，而噪声里最像巫师的
   8 个窗口只有 0.15~0.17 —— 占比既保住召回、又把噪声挡在外面。
2. **`any` 组支持占比键**（前置 `%`，如 `"%minecraft:polished_blackstone_bricks": 0.26`）。
   判据 = 「占比够高」**或**「次要特征齐备」，两条通路谁满足都行 —— 这样能**同时**兼容
   「被淹没」（走占比）和「完整露出但配料比例不同」（走次要特征）。

三类指纹表最终都改成「主料绝对下限 + 并列通路」：

```json
// 巫师
"anchors": {"minecraft:polished_blackstone_bricks": 100},
"any": [
  {"%minecraft:polished_blackstone_bricks": 0.26},
  {"minecraft:cracked_polished_blackstone_bricks": 30,
   "minecraft:blackstone": 55, "minecraft:deepslate_bricks": 18}
]
```

**淹没存活率实测**（`_ruincurve.py`，按「遗迹」口径，20 次模拟淹没）：

```
巫师：旧判据 17/20 → 淹没 50% 归零；新判据 18/20 → 淹没 70% 仍保 18
武士：旧判据  7/43 → 淹没 50% 归零；新判据  9/43
白金：旧判据  2/2  → 淹没 50% 归零；新判据  2/2  存活到 50%
```

先倒的锚点用 `_firstfail.py` 定位：巫师是 `pbrick`（漏 56→129 次），武士是 `netherrack`（119→58 次）。

#### ⚠️ 标定时踩过的坑：占比阈值过拟合（最重要的一次）

占比阈值 0.26 起初只在 coordbridge 的真实 chunk 上标定。跑到 **C 段（140 个真实 Xaero
region）**时发现巫师命中从 57 **掉到 51** —— 出现了**过拟合回退**。

用 `_ab_cmp.py` 逐窗口对照，定位为 **18 个「旧过新不过」窗口**，全都是**大巫师遗迹的偏移窗口**
（如 `polished_blackstone_bricks=493 / blackstone=246 / cracked=141` 这种**完整实例**），
它们的占比只有 0.245~0.257，被 0.26 卡掉了。

**修法**：不调阈值（调低会放进噪声），而是把「占比」与「次要特征齐备」做成 **`any` 并列通路**
——完整实例走次要特征那条路，被淹没的走占比那条路，两边都不漏。
修后 `_ab_cmp.py`：Xaero 上「旧过新不过 = 0」，且**净增 14 个**。

> 这印证了 3.5 节那条方法论：**硬特征的阈值尽量写成「家族合计」/「通路并列」，别钉在单个量上**。
> 单点标定出来的阈值，换个数据集就会反过来咬人。

### 3.7 武士的「恒定构件」通路：淹没段结论的一个例外（本轮）

**现象**：用户再次报「这里面有**两个武士**的遗迹也没有检测到」（附图，玩家 `(4754, -39155.6)`、
视野 520 格）。截图上方 `≈(4744,-39224)` 与下方 `≈(4660,-38750)` 各一座武士。

**先确认一件事：截图上的地形就是模组落盘的数据。** HUD 第一行 `DIM1 / $mem` 说明当前图层是
**内存直读合成图**（读 `~/.coordbridge/chunks/` 里模组写的区块再渲染 region）。所以窗口直方图里
出现的方块名，就是**建筑高出地形基准**（height 56/57）的那部分用料；低于基准的列写 NODATA
（`0xFFFF`），不出现在直方图里。用 `_shoot.py` 按真实图层渲染 `(4754,-39156)` 与截图**逐像素吻合**，
确认了这个口径。

**根因**：这两座武士的**下界岩 / 磨制玄武岩被地形整个埋掉**——实测 `netherrack=9~10`、
`polished_basalt=0`。而旧指纹把 `polished_basalt ≥ 5` 钉在 `anchors` 上 ⇒ **两座必漏**。
（`_probe_loc.py 4754 -39156 480` 把它定位到「白金星殿:… 武士的修行地:polished_basalt 0<5」，
即卡在这一条。）

**关键观察：武士的用料要分成两半看。**

| 类别 | 构件 | 露出稳定性 | 17 座实例实测 |
|---|---|---|---|
| **恒定构件** | 末地石砖系 / 净下界砖系 / 诡异台阶 / 绯红系，共 16 项 | 每次完整露出 | 合计 **116~197** |
| **可变构件** | 下界岩、磨制玄武岩 | 会被地形全埋 | 下界岩 5~200、玄武岩 **0**~68 |

`_clusters.py` 在真机上做 chunk 级 8 连通聚类（236 簇），把这两半的分离度打出来：

```
@samurai_core 排序：第 1~17 名 = 116 ~ 197
                    第 18 名   = 66（骤降）
                    其余全部建筑 ≤ 66（巫师 / 白金星殿 / 紫珀殿 / 幽匿殿 …）
```

间隔很宽 ⇒ 阈值取 **90** 很安全。

**修法**：`ruins.json` version 3 → 4，新增家族 `samurai_core`（16 项），武士判据改为

```json
"anchors": {"@end_brick": 30},          // ← 移除 polished_basalt，它是可变构件
"any": [
  {"@samurai_core": 90},                // ← 新增：恒定构件合计通路
  {"%minecraft:netherrack": 0.12},
  {"minecraft:netherrack": 60, "minecraft:polished_basalt": 8, "@crimson": 25}
]
```

#### ⚠️ 这条通路必须用「绝对数」，不能用占比（与 3.6 节结论相反）

3.6 节的结论是「占比抗淹没」，但**武士这条不能照搬**，理由必须写清楚，否则以后有人会
"顺手"把 `@samurai_core` 改成 `%@samurai_core`：

* 被埋掉的**只是低处的可变构件**，恒定构件在高处**几乎不缩水**（17 座实例全是 116~197 的满配）；
* 于是绝对数是稳的；而占比实测**反而更差**：武士 0.36~0.80，其它建筑里也有 0.66~1.14 的，
  **分不开**。

> 「绝对数 vs 占比」不是对错问题，是**哪一种量在淹没下保持不变**的问题：
> 巫师的可变部分占比高且会被整体压缩 ⇒ 用占比；武士的**特征部分本身就在高处、不缩水**
> ⇒ 用绝对数。**换一类建筑就要重新判断一次**，不能照抄。

#### 两条边界，用负例压住

`samurai_core` **刻意不含** `end_stone_bricks`、也不含任何菌岩（nylium），否则会串类：

* **紫珀殿**：`end_stone_bricks 68` + 紫珀系一大堆，但**一个恒定构件都没有**（core=0）；
* **幽匿殿**：`end_stone_bricks 66` + 真带 `warped_slab 16` / `nether_brick_fence 14`，
  但 core 合计只有 40 出头，到不了 90。

另外 `dirt` 要**并进**武士的 `blocks`：每座都有 18~33 列、且都在地形之上（是建筑自带的土质演武场），
不放进去纯度会虚低到 0.79 而漏检。

**效果**：
* `_probe_loc.py 4754 -39156 480`：上方那座**已命中**（纯度 0.98），原本已命中的几个窗口纯度 0.85 → 0.97；
* **D 段真机**：命中 9 处 → **11 处（7 巫师 + 4 武士）**，新增的两座武士 `@samurai_core=112/164`，

## 5. 开局静默：基线扫描

启动时先在**后台线程**做一次基线扫描（实测 **19~21 秒 / 2.9 万个区块**），


三条理由：

1. **语义**：开局时地图上早就有那十几处遗迹了，不该一启动就报警（否则一次全响）；
2. **效果**：判定窗口是 5x5 区块，先把邻域读进来，之后新落的区块一进窗口就能立刻判对；
3. **覆盖所有维度**：不然玩家第一趟跑末地时，那一万多个文件会落到主线程上卡十几秒。

之后每 0.6 秒扫一轮（每轮最多解析 320 个新区块）。**换局（`sid` 变化）不重扫**：
模组的版本号会重排，按「变了就重扫」处理会卡主线程十几秒并重放历史；
这里直接把当前版本号当新基线，内存直方图保留（旧区块文件还在磁盘上，数据依然有效，
留着才能让判定窗口完整）。

## 9. 支持 1.20.1：为什么**不需要**第二个 jar

需求原话：「做一份1.20.1可以用的版本」。

### 9.1 先搞清楚版本差异到底在哪

模组的关键性质：**全程只用「字符串 + `Class.forName`」，不链接任何 Minecraft 类**
（`Names.java` 里全是字符串，`build_mod.py` 用 javac 编译时 classpath 上只有
fabric-loader，根本没有 MC jar）。所以「换 MC 版本」能坏掉模组的唯一途径就是
**intermediary 名字变了**，跟 MC 的代码逻辑无关。

于是问题变成一个可测的问题：**1.20.1 与 1.20.4 的这批名字一样吗？**

### 9.2 做法：用**那个版本自己的**两份映射重新推导

不能照抄。官方名相同不等于 intermediary 相同 —— intermediary 是按每个版本的
obf 名生成的，Mojang 在相邻版本里改个字段名，obf 变了，intermediary 就可能跟着变。
所以把 `mapbridge.py` / `modmap.py` 参数化，对每个版本各取两份资源：

| 资源 | 来源（1.20.1） |
|---|---|
| Mojang 官方映射 | `piston-data.mojang.com/.../client.txt`，**sha1 校验通过**（`6c48521e...`，8001795 字节） |
| Fabric intermediary | 本机 `D:\config\mc\.minecraft\libraries\net\fabricmc\intermediary\1.20.1\intermediary-1.20.1.jar` |

`python modmap.py --compare 1.20.1 1.20.4` 的结果：

```
** 完全一致 **：63 项（20 类 + 9 字段 + 17 方法 + 17 描述符）在两版本间没有任何差异。
```

再把 1.20.2 / 1.20.3 / 1.20.5 也各比一遍 —— **同样是 63/63 全同**（1.20.3 的
`client.txt` 与 1.20.4 是同一份，都是 8897012 字节）。

### 9.3 结论：一个 jar 通吃，上界卡在 1.20.5

`fabric.mod.json` 从 `~1.20.4` 改成 **`>=1.20.1 <1.20.5`**，`version` 提到 `1.2.0`。

- **为什么不是「做一份 1.20.1 的 jar」**：名字既然一样，分版本构建只会制造
  「拿错 jar」这种新故障。一个 jar 反而更不容易出错。
- **为什么上界是 `<1.20.5` 而不是更远**：1.20.5 那次的 63 项**也相同**，但那是
  注册表大改版（`BuiltInRegistries` → `Registries`），行为没在真机验过。
  名字对得上只说明「反射能解析到」，不等于「拿到的数据是对的」，所以不擅自宣称支持。

### 9.4 版本谓词是**交给真实 fabric-loader** 验的，不是推断的

`fabric.mod.json` 里写错一个字符，Fabric 会**拒绝加载整个模组**。所以不能凭印象写。
本机有真实的 loader jar，直接调用它的 `VersionPredicateParser` 解析再逐版本求值：

```
>=1.20.1 <1.20.5   OK   1.20.1=true 1.20.2=true 1.20.4=true 1.20.5=false 1.21=false
```

loader **0.14.22 / 0.16.13 / 0.16.14 三个版本各验一遍**，结果一致（0.14.22 是
本机 1.20.1 实例实际在用的那个）。

### 9.5 顺带发现并修掉的 7 个问题

| # | 问题 | 为什么危险 | 修法 |
|---|---|---|---|
| 1 | `modmap.py --compare` 只比**名字**，不比**描述符** | 名字对而描述符错时，`Ref` 的运行期自检会判「找不到」，整条取方块链路**静默失效** —— 正是第 6 节那类最难受的故障 | 加比 `resolve_full()` 的 `desc`（就是 `Names.sigs()` 的内容） |
| 2 | `modmap.py --check` **从不校验 `sigs()` 描述符表** | 名字核对了，描述符表却没人管；改错一样静默失效 | `--check` 补上 17 条描述符的逐字核对 |
| 3 | `CoordBridge.java` 手抄了一份常量副本 | 与 `Names.java` 双份维护，漂移后表现是 `status.txt` 报**假错**（明明能用却报 NOT FOUND），极难查 | 常量统一取 `Names.*`，删掉副本 |
| 4 | jar 文件名（`1.0.0`）与 `fabric.mod.json` 的 `version`（`1.1.0`）**不一致** | 交接给人的东西自相矛盾 | `build_mod.py` 从 metadata 读版本号推导文件名，杜绝再漂 |
| 5 | 装新 jar 时**旧 jar 删不掉会留下双 jar** | 两个同 mod id 的 jar 并存，Fabric 判重复并**拒绝加载整个模组**，而报错指向 `mods\`，很难联想到是本工具造成的 | 改成**先清旧、清不掉就整个跳过不装**。这条是实打实踩到的：装的时候用户的游戏正开着，`coordbridge-1.0.0.jar` 被 JVM 占用删不掉 |
| 6 | 编译用的 loader 取「本机最高版」 | 可能无意中用到只有新 loader 才有的 API | 改成取**满足 ≥0.14 的最低版**，对着「声明支持的最低版本」编译 |
| 7 | `gen_stubs.py` 的桩类与 `Names.java` 无同步校验 | 桩类名字是写死的；一旦脱节，离线验证就从「证明」退化成「自证」，表面上仍一路 OK | 加双向核对：`Names.java` 每个常量都得在桩源码里出现；每个桩 `class_xxx` 都得被 `Names.java` 引用 |

### 9.6 Python 侧也核过了

- **1.20.1 的 Xaero 数据能解析**：拿本机 1.20.1 实例里 1264 个真实 region 抽样 40 个，
  `strict=True`（要求恰好消费完整个文件）**40/40 通过**，格式版本 `(6,7)`；
  1.20.4 的是 `(6,8)`。解析器本来就按文件头的 `minor` 分档，两种都覆盖。
  （`xaero_region.py` 不用改。）
- **底图目录定位**：`followmap/paths.py` 靠的是「模组 `status.txt` 里记的游戏目录 +
  `coords.json` 里的服务器 host」，与 MC 版本无关，1.20.1 实例照样能自动定位。
- `diagnose.py` 不绑版本也不绑 jar 文件名，无需改动。

## 10. 压低地图延迟（2026-10-11）

> 需求原话：「给出可以压低地图延迟的方案」。

### 10.1 先定位：延迟花在哪

新增分段探针 `_modtest/probe_latency.py`（真机数据逐段量 + 合成数据量端到端）。
直接给 `FollowApp.step()` 插桩（2026-10-11，真机 bridge 坐标源，40 帧）：

| 段 | 改前 | 说明 |
|---|---|---|
| `step()` 每帧（中位） | **310 ms** | 帧周期 = 250 + 310 = **560ms ≈ 1.8fps** |
| `resolver.candidates()` | **270 ms/帧** | 占整帧 **91%** |
| `_pairs()` | 366 ms（每 15s 一次） | 周期性卡顿 |
| `TileStore.dims()` | 57 ms | 三处调用者各扫一遍 |
| `MapView.render`（真画图） | 7.7 ms | — |

根因：`app._resolve_xaero()` **每帧**都调 `DimResolver.candidates(fix.dim)` 来回答
「玩家在哪张子图」，而这个函数**没有任何缓存**，每次都对所有候选目录做一轮
`os.listdir` + 逐文件 `getmtime`。实测 `candidates('minecraft:overworld')` = **316 ms**
（103 个候选目录）、`candidates('minecraft:the_end')` = **211 ms**。

> ⚠️ 这个坑在 `--selftest` 里**看不见**：自检用 `--source demo`，`fix.dim` 为空，
> `_resolve_xaero` 走的是 demo 分支，`candidates()` 根本不会被调用 —— 自检里 11 fps
> 看着很正常。必须用 `--source bridge`（真机）插桩才暴露。

### 10.2 改了什么

1. **`TileStore.scan_dir()`**：一次 `os.scandir` 同时拿到「region 坐标集合」与「最新 mtime」
   （`DirEntry.stat()` 走 Win32 目录枚举自带数据，不额外产生系统调用），带 TTL 缓存。
   `_existing()` / `last_activity()` / `_pairs()` / `build_dim_map()` 全部改用它。
2. **`DimResolver.candidates()` 加 2 秒结果缓存**（Xaero 自己 60 秒才落一次盘，不会看漏）；
   `_all_pairs()` 30s → 60s。
3. **`TileStore.dims()` 加 5 秒缓存**（42ms/次，三处调用者）。
4. **`_pairs()` TTL 15s → 60s**，并改用一次扫描。
5. **`MemLayer._index` 改 mtime 门控**（原 1.0s 硬 TTL）：每帧只多一次 `os.stat`，
   文件没变就不重新解析 JSON；读到截断 JSON 时**沿用上次的值**（防止误判「无数据」而整屏退回底图）。
6. **`CompositeStore` 热 region 就地重建**（令牌桶限速 5/s、最多攒 2）：热重建实测
   40~50ms，当帧做完，省掉「丢后台 → 下一帧才画」的一整帧；冷建（420ms）仍然只走后台。
   新增 `--no-inline` 可关。
7. **`hudtext.render` 加 LRU 缓存**；**`TileStore.exist_ttl` 1.5s → 0.6s**。
8. **`--interval` 默认 250 → 120**（渲染一帧只要 ~8ms，帧周期是延迟的主要线性项）。

### 10.3 改前改后

| 指标 | 改前 | 改后 |
|---|---|---|
| `step()` 每帧（中位） | **310 ms** | **1.8 ms**（最慢 200ms 只出现在首帧冷扫） |
| `resolver.candidates()` | 270 ms/帧 | 2.2 ms/帧（绝大多数命中缓存 ≈0.001ms） |
| `TileStore.dims()` | 57 ms | ≈0（5s 缓存） |
| HUD 文字渲染 4 行 | 5.1 ms | 0.002 ms（LRU 命中） |
| 每帧固定开销合计 | 19.6 ms | **7.8 ms** |
| 帧周期（`--interval 250`） | 560 ms / 1.8 fps | 128 ms / 7.8 fps |

### 11.2 如果以后要恢复：技术结论仍然有效，但别再犯同一个错

当初验证得很扎实，下面几条结论可复用：

- **Xaero 确实留了外部注入口**：`xaero.common.minimap.waypoints.WaypointsManager` 的静态方法
  `getCustomWaypoints(String)` 返回一个 `Hashtable<Integer, Waypoint>`
  （静态、自带同步 —— 后台线程写不会和渲染线程撞 `ConcurrentModificationException`）；
  渲染器 `WaypointsIngameRenderer` 会把它的**全部内容**合并进渲染列表，**不按 containerID 过滤**。
- **签名四年没漂移**：遍历 18 个 Xaero 小地图 jar（22.16.0 → 25.2.10，跨 Fabric/Forge，
  MC 1.12 → 1.21.4）签名**全部一致**，所以不必按 Xaero 版本分别构建。
- **仍然不需要 Gradle**：全程「字符串 + `Class.forName`」，不链接任何 Xaero 类。
- **`customWaypoints` 没有维度概念**，渲染器只看当前维度 —— 注入方必须自己按维度过滤，
  换维度时先清空再重灌。

**恢复时唯一必须改的是「标哪些点」**：只注入 `poll()` 返回的**本次新命中**，
而不是读 `found_ruins.json` 的全量历史；退出时清空口袋。
这样地图上只会出现「这趟跑图新撞见的」，历史命中仍然只留在 `followmap` 窗口与
`out/found_ruins.json` 里。

## 12. 「直接用方块 id 判定」的真机检验（2026-10-11）

用户提出：末地出现**黑石**必然是巫师遗迹，出现**石砖**必然是白金遗迹，问能不能据此简化判据。
用真机落盘的 **71124 个末地 chunk** 全量跑了一遍（`_modtest/probe_blockid_rule.py` /
`probe_blockid_rule2.py`），结论如下。

### 12.1 先厘清一件事：方块 id 本来就在读

模组每个 chunk 存的就是「256 列地表方块的 id + 高度」，`ruins.py` 的直方图就是 id 计数。
所以「读 id」不是新能力，问题只在于**判据能不能简化成「出现某 id 即判定」**。

### 12.2 两个 id 选错了（建筑级 76 座：白金 4 / 武士 35 / 巫师 37）

| 方块 id | 巫师 | 武士 | 白金 | 结论 |
|---|---|---|---|---|
| `polished_blackstone_bricks`（磨制黑石砖） | **67118，37/37 座** | 0 | 0 | ✅ 巫师独占 |
| `blackstone`（原料黑石） | 24243，36/37 | **524，29/35 座** | 0 | ❌ 武士也有 |
| `blackstone_stairs` | 9 | **344，35/35 座** | 0 | 其实是**武士**特征 |
| `gilded_blackstone` | 46 | **1280，33/35 座** | 0 | 其实是**武士**特征 |
| `infested_stone_bricks`（虫蛀石砖） | 0 | 0 | **3081，4/4 座** | ✅ 白金独占 |
| `stone_bricks`（普通石砖） | **157，35/37 座** | 0 | **0** | ❌ **方向完全反了** |
| 石砖系合计（8 项） | ≤14 | 0 | 968~1058 | ✅ 可分，余量 69 倍 |

**关键**：白金用的石砖是 `stone_brick_stairs` / `stone_brick_slab` / `chiseled_stone_bricks` /
`infested_stone_bricks`，**恰恰不含普通 `stone_bricks`**；而普通 `stone_bricks` 在 35/37 座巫师里
都有（每座 3~6 块，装饰件）。按「出现 stone_bricks ⇒ 白金」判会**把巫师全判成白金**。

### 12.3 换成正确 id 后，「出现即判定」仍不能单独用

把候选判据真的当判据跑一遍（窗口级，阈值扫描）：

| 判据 | 报出 | 真目标 | 误报 |
|---|---|---|---|
| `polished_blackstone_bricks >= 20 ⇒ 巫师` | 38 座 | 37 | **1** |
| `polished_blackstone_bricks >= 138 ⇒ 巫师` | 36 座 | 36 | 0（但漏 1 座） |
| `blackstone >= 1 ⇒ 巫师` | 66 座 | 36 | **30（全是武士）** |
| `blackstone >= 20 ⇒ 巫师` | 35 座 | 35 | 0 |
| `infested_stone_bricks >= 1 ⇒ 白金` | 4 座 | **4** | **0** |
| `stone_bricks >= 1 ⇒ 白金` | 35 座 | **0** | **35（全是巫师）** |

那 1 座可疑目标在 `(4586,-46944)`：`soul_soil=175 + polished_blackstone_bricks=109`，
距最近真巫师 **917 方块**。既可能是被纯度卡掉的小遗迹（潜在漏检），也可能是一座非目标小建筑。

**为什么还是不能只靠"出现"**：地形淹没会等比压低计数，区间会重叠。
实测巫师 `polished_blackstone_bricks` 最低 138，而紫珀殿/幽匿殿的边缘窗口有 **227 / 192**
（`sculk` 或 `purpur` 主导）——数量上分不开，只能靠纯度。
（经核实这两处距真巫师重心仅 **26 / 30 方块**，是巫师本体边缘，不是别的建筑。）

### 12.4 结论

- 用户的直觉方向是对的，而且**这两条已经就是现在的 `anchors`**：
  巫师 = `polished_blackstone_bricks >= 100`，白金 = `infested_stone_bricks >= 35` + `red_wool >= 3`。
- 需要修正的表述是：黑石 → **磨制黑石砖**（不是原料黑石）；石砖 → **虫蛀石砖 / 石砖系合计**
  （**不是**普通 `stone_bricks`）。
- `any` 组 + 纯度这一层**不能省**：它负责挡住淹没导致的计数缩水和跨类型串类。
  本轮未改 `ruins.json`（现有判据已覆盖这两条，且回归全绿）。
