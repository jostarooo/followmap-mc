# 方案 C · 第二屏「外部跟随地图」

跑图时把一块**无边框、置顶**的小窗口钉在副屏上，每 150ms 以玩家为中心重绘
真实地图数据，不用手动拖官方地图。

数据有**两层**，自动合成：

- **内存层（实时）** —— `coordbridge` 模组直读游戏内存里已加载的区块，延迟 < 1 秒；
- **Xaero 层（历史底图）** —— 读 Xaero 的 `region.zip`，覆盖全部探索过的区域，但**天生滞后**
  （Xaero 落盘是硬编码 60 秒一次，见下文）。

## 它怎么工作

```
┌── 内存层：实时（延迟 < 1 秒）────────────────────────────────────┐
│  coordbridge 模组直读游戏内存中已加载的区块                        │
│     Minecraft.level -> ClientChunkCache.Storage.chunks -> LevelChunk
│     每列 1 次 getHeight(WORLD_SURFACE) + 1 次 getBlockState        │
│        │                                                          │
│        ▼  ~/.coordbridge/chunks/<维度>/r<rx>/r<rz>/<cx>_<cz>.bin   │
│     MemLayer 解析 -> 512×512 RGBA（未覆盖处透明）                  │
└──────────────────────────────────────────────────────────────────┘
                              │
┌── Xaero 层：历史底图（滞后 20~60 秒）────────────────────────────┐
│  XaeroWorldMap/Multiplayer_mcfkcs.com/<维度>/<mw$default|cm$N>/*.zip
│        │  xaero_region.py 解析                                    │
│        ▼                                                          │
│     TileStore  解析 + 金字塔着色 -> RGBA 瓦片（内存 LRU + 磁盘缓存）│
└──────────────────────────────────────────────────────────────────┘
                              │
        CompositeStore：把内存层 alpha 合成在 Xaero 底图之上
                              │
                              ▼
        MapView.render  以玩家为中心裁一屏，叠网格/POI/玩家标记/HUD
                              │
                              ▼
        FollowApp  150ms 循环：取坐标 -> 解析维度 -> 渲染 -> 送进 Tk 窗口
```

## 玩家坐标从哪来（三级回退）

| 优先级 | 来源 | 说明 |
|---|---|---|
| 1 | **CoordBridge 模组** | 纯反射 Fabric client mod，10Hz 把坐标/维度/服务器写进 `~/.coordbridge/coords.json`。精确、无延迟、**带维度信息**。 |
| 2 | **截屏 OCR** | `PrintWindow` 抓游戏窗口 → 模板匹配小地图上的坐标文本。精度 100%，真实地形背景召回约 75%，靠多帧投票兜底。 |
| 3 | **手动 / Demo** | 无游戏时用来验证与调试。 |

> 模组**必须重启游戏**才会生效（改过 jar 也一样）。重启后随便动一下，`~/.coordbridge/` 下会出现
> `coords.json`（坐标）、`status.txt`（自检）、`scan_status.txt`（区块扫描器状态）和
> `chunks/`（内存直读出来的区块数据）。没写出来就看 `status.txt` 里的报错。

## 用法

```bat
:: 双击（推荐）
app\启动跟随地图.bat            :: 520px，150ms，图层 auto
app\启动跟随地图-静默.bat       :: 无控制台
app\诊断.bat                    :: 起不来时先跑这个，逐步定位
app\打包便携版.bat              :: 打一份能拷到别的电脑用的最小包（见「移植到另一台电脑」）

:: 启动器可带参数：位置参数是 SIZE INTERVAL LAYER，之后的所有参数原样转给 app.py
app\启动跟随地图.bat 640 100 surface --selfclose 5
app\启动跟随地图.bat 520 150 auto --dim null --no-grid

:: 或命令行
python followmap\app.py --size 480 --interval 200 --layer auto
python followmap\app.py --source demo          :: 不用游戏，主城走一圈
python followmap\app.py --map xaero            :: 只用 Xaero（会滞后，用来对比）
python followmap\app.py --dim null --mw mw$default --x -6900 --z 13060
python followmap\app.py --selftest 40          :: 无窗口自检，落盘 out/follow/
```

> **关于「图层」这件事（实测结论）**
> 同一维度 `dimensionTypeId` 在服务器上会对应好几个目录。判断哪个是"当前在用的"，
> **不能按名字猜**（`cm$*` 不一定是"地下"，`mw*` 也不一定是"地表"）。
> 实测例：末地下 `DIM1/cm$1` 是 2 秒前刚写入的活动图，而 `DIM1/mw$default` 最后写入
> 是 **20 天前**且 z 只覆盖到 17408 —— 玩家在 z=48329，那图在脚下根本没数据。
> 所以默认 `auto` 按**最近写入时间**选；万一选错，程序会去候选图里找
> 「玩家所在 region 真的有数据」的那个自动切换，并在 HUD 上说明。

常用参数：

| 参数 | 说明 |
|---|---|
| `--size 520` / `--size 640x400` | 窗口尺寸（**启动后仍可改**：`+`/`-`/`0`、Ctrl+滚轮、右键拖右下角，见「窗口快捷键」） |
| `--interval 120` | 重绘周期 ms。**这是地图延迟最直接的一档**：延迟 ≈ 帧周期 × 帧数，而渲染一帧只要 ~8ms，所以调小很划算。120 是默认值（端到端 127ms）；想更跟手可到 80；笔记本挂机想省电可到 200~500 |
| `--no-inline` | 关掉「热 region 就地重建」。默认**开**：某个 region 之前建过、只有几个 chunk 变了时（实测重建 40~50ms），就在当帧直接建完，省掉「丢后台 → 下一帧才画」的整整一帧。冷建（要 420ms）永远只走后台，不受这个开关影响 |
| `--layer auto\|surface\|cave` | 默认 `auto`：选该维度下**最近写入**的那张图（实测最准）。`surface` 只看 `mw*`，`cave` 只看 `cm*` —— 只在明确知道玩家在哪一层时才手动指定。 |
| `--map auto\|mem\|xaero` | 默认 `auto`：内存直读层 + Xaero 底图合成（**跟得上跑图的唯一模式**）。`xaero` 只用旧地图（会滞后半分钟以上，仅用于对比/排错）。 |
| `--source auto\|bridge\|ocr\|manual\|demo` | 强制指定坐标源 |
| `--dim null --mw mw$default` | 手动锁定维度+子图（不看游戏给的维度） |
| `--zoom 2` | 初始缩放：每像素代表多少方块，自动规整到 **1/2/4/8** 四档之一。默认 1（视野=窗口宽度） |
| `--no-prewarm` | 关掉视口预取（排错用；正常别关，关了会明显跟不上跑图） |
| `--poi poi.json` | 遗迹标记文件 |
| `--server <目录>` | Xaero 的「服务器」目录（里面按维度分子目录）。**留空 = 自动定位**，见「移植到另一台电脑」。换电脑后一般不用手填。 |
| `--ruin-alert auto\|both\|sound\|shake\|flag\|off` | **稀有遗迹（巫师/武士/白金）提醒方式**。默认 `auto` = 水滴音（**连响三下**）+ 任务栏闪烁 + 地图打点，**不抖窗口**；`sound` 只出声、`both` 再加上窗口抖动、`shake` 只抖、`flag` 只闪、`off` 只打点不出声 |
| `--ruin-volume 1.5` | 水滴音音量 0.2~3.0。波形峰值已归一化到满刻度，`>1` 走 tanh 软削波继续推响度（**峰值不变，不会数字破音**）；实测穿视频声用 1.5~2.0 |
| `--ruin-repeat 3` | 水滴音连响几下（默认 3）。**这是能从视频声里穿出来的关键**，直接烧进 wav，不靠循环播放 |
| `--no-ruin` | 完全关掉遗迹识别提醒 |

## 移植到另一台电脑

需求原话：「这个程序如果发给在外地的另外一台电脑上使用可以直接用吗」。
**结论：不能双击就用，但只有 3 件事要准备**（代码侧已经改成不用手改路径）。

### 一、对方要准备什么

| # | 项 | 说明 |
|---|---|---|
| 1 | **Python 3.9+** | 装的时侯勾 *Add python.exe to PATH*。三个 `.bat` 的查找顺序是「本机固定路径 → `python` → `py -3`」，所以**没勾也能起来**（python.org 的安装器会把 `py.exe` 放进 `C:\Windows`） |
| 2 | `pip install -r requirements.txt` | 运行期只依赖 **Pillow + numpy**。opencv / matplotlib / lxml / python-docx 只有项目根那些离线分析脚本用，**不用装** |
| 3 | **Minecraft 1.20.1 ~ 1.20.4 + Fabric** | 模组声明 `minecraft: >=1.20.1 <1.20.5`。**同一个 jar 这几个版本通用**，不用挑：模组全程只用「字符串 + 反射」，不链接任何 Minecraft 类；需要的 20 类 / 9 字段 / 17 方法 / 17 描述符在这几个版本间**逐字相同**（`python modmap.py --compare 1.20.1 1.20.4` → 63 项完全一致）。真换到别的版本（如 1.20.5+、1.19.x）会**静默失效**，`~/.coordbridge/status.txt` 的自检会写出来 |
| 4 | **CoordBridge 模组** | 把 `coordbridge/coordbridge-<版本>.jar`（当前 `1.2.0`）丢进 `.minecraft\mods\`。**这是唯一的数据来源**，不装就没有坐标也没有地形 |
| 5 | **Xaero's World Map** | 提供历史底图。不装也能跑，只是老区域没有底图（`$mem` 内存层不依赖它） |
| 6 | 进同一个服务器 | 用途是「刷视频时也听得到稀有遗迹提醒」，得在同服跑图才有意义 |

装完模组**必须重启游戏**。进一次服务器后 `~/.coordbridge\` 下才会有 `coords.json` / `chunks\`。

> **模组支持 1.20.1 ~ 1.20.4，同一个 jar 通吃。**
> 模组只跟「intermediary 名字」绑版本，跟 MC 代码无关：它是纯反射的，不链接任何 MC 类，
> 所以换版本坏掉的唯一方式是名字变了。而这四版的 63 项（20 类 + 9 字段 + 17 方法 +
> 17 描述符）实测**逐字相同**，因此不需要「1.20.1 专用版」这种东西。
>
> ```bat
> python build_mod.py --no-install     :: 只编译，不安装
> python build_mod.py --mc 1.20.1      :: 编译并装进 1.20.1 的 mods
> python build_mod.py --install-all    :: 装进本机所有「在支持范围内」的实例
> python _modtest\test_modref.py       :: 验证纯反射 / 常量表一致 / 版本谓词范围三件事
> python modmap.py --compare 1.20.1 1.20.4   :: 自己再比一遍两版本的名字与描述符
> python modmap.py --fetch 1.20.2      :: 换版本时先把那版的映射下下来（唯一会联网的用法）
> ```
>
> ⚠️ 安装时会**先清掉旧的 `coordbridge-*.jar`，清干净了才拷新的**。如果旧 jar 删不掉
> （正在玩游戏，jar 被 JVM 占用），**这次就整个跳过不装**——留着两个同 mod id 的 jar，
> Fabric 会判重复并**拒绝加载整个模组**，而报错指向 `mods\` 目录，很难联想到是这里造成的。

### 二、打包

```bat
app\打包便携版.bat          :: 输出 dist\FollowMap-Portable（34 个文件 / 0.6 MB）+ 同名 .zip（262 KB）
```

按**白名单**收文件，只收运行必需的：程序本体、`ruins.json`/`poi.json`/`block_colors.json`、
`assets\`、`cache\font_ascii.png`、模组 jar。**不收** `_modtest/`、`out/`、
`cache/{cls,mappings,memtiles,tiles}`、40+ 张调试 PNG、
以及本机的 `server_path.txt`（带过去只会把对方带偏，让它自己扫一次）。
生成物里附带 `README-移植说明.md`，对方照着做即可。

打完包还会做一道**清洁性检查**：`out/found_ruins.json` 之类的运行期产物一旦混进来（例如打包后在 `dist/` 里跑过程序），会报出来并自动删除。那是个**去重库**，带过去会让里面那几处遗迹被当成"已发现"永久静音。要验证请把整个文件夹拷出去再跑。

> 目录名故意用纯 ASCII `FollowMap-Portable`：带中文的路径在部分云盘/压缩工具里会被改编码。

### 三、Xaero 地图目录怎么找（唯一需要动脑的一环）

**路径是自动定位的**，`--server` 的默认值不再是硬编码。顺序：

| 顺序 | 来源 | 说明 |
|---|---|---|
| 1 | `--server <目录>` | 命令行显式指定，最高优先级 |
| 2 | `FOLLOWMAP_XAERO` | 环境变量 |
| 3 | `server_path.txt` | 程序同目录，一行。可写服务器目录，也可只写 `XaeroWorldMap` 那一层（会自动往下挑服务器） |
| 4 | **模组 `status.txt` 里记录的游戏目录** | **最可靠**：模组自己写了 `cwd : <游戏目录>`，`XaeroWorldMap` 就在它下面。不用猜 |
| 5 | `cache/server_path.auto.txt` | **上一次盘符扫描的结果**（省下 9 秒重扫）。故意与 `server_path.txt` 分开：人工口子优先级更高，自动结果排在模组数据之下，**模组一跑过就能自动纠正错猜** |
| 6 | 常见启动器位置扫描 | 官方启动器 / CurseForge / Prism / Modrinth / HMCL / PCL2 附近 |
| 7 | 老机器上的默认位置 | 兜底，保证以前能跑的一直能跑 |
| 8 | 盘符扫描 | 最后手段（本机把整合包放在 `D:\config\game\mc\pcl2` 下，不属于任何标准位置）。成功后会写进第 5 条 |

**「挑哪个服务器目录」也不靠猜**：`XaeroWorldMap` 下往往有多个 `Multiplayer_*`
（本机就有 5 个）。这里读 `~/.coordbridge/coords.json` 里模组记录的**当前服务器 host**，
而 Xaero 的目录名恰好就是 `Multiplayer_<host>` —— 匹配上直接用；匹配不上才退回
「region 数据最新」。所以「玩家刚去过别的服务器」也不会挑错。

启动后第一行会打印用的是哪个目录、从哪找到的：

```
[followmap] Xaero 底图 : D:\...\XaeroWorldMap\Multiplayer_xxx.com
[followmap] 定位来源   : 模组 status.txt 的游戏目录（匹配当前服务器 xxx.com）
```

失败时（`!! 底图目录不可用`）**不会崩**：`TileStore` 对不存在的目录是容错的，
内存直读层照常出图，只是历史区域空白。这时按上表第 1~3 条手工指定即可。
`诊断.bat` 的第 4 步会把「模组记录的目录 / 服务器线索 / 选用的目录 / 定位来源」全打出来。

## 缩放：方向和档位都跟 Xaero 一致

- **滚轮上滚 = 放大**（看清细节，视野变小），**下滚 = 缩小**（看得更远）。`z` / `x` 同义。
- 档位只有 **1 / 2 / 4 / 8**（每像素代表多少方块）。取 2 的幂是为了让每一档都是上一档的
  **精确 NEAREST 降采样**，于是"一次渲染、逐级降采样"与"直接按该档渲染"结果完全相同。
- 窗口 560px 时：1px=1 → 视野 560 格；1px=8 → 视野 4480 格。

> 为什么要锁死档位而不是逐级 ±1：缩放档位一变，缓存里所有瓦片都失效。早先的实现
> 每换一档都要**重新解析 + 重新着色整屏**（实测每片 region 约 150ms，整屏要 0.6 秒，
> 连续滚轮就是一路黑屏）。现在改成**金字塔**：解析一次、着色一次，再降采样出全部档位，
> 切档实测 5~10ms（磁盘命中）到 0.005ms（内存命中）。

## 性能：实测数据与天花板

单帧渲染（560px、瓦片已就绪）：

| 档位 | 帧耗时中位 | 视野 |
|---|---|---|
| 1px=1 | 3.0 ms | 560 格 |
| 1px=2 | 2.0 ms | 1120 格 |
| 1px=4 | 1.5 ms | 2240 格 |
| 1px=8 | 1.7 ms | 4480 格 |

跑图模拟（40 帧，真实 region 数据，每帧预取整屏+一圈）：步行 15 / 鞘翅 33 / 火箭 66 m/s
三种速度下，**整屏全黑的帧数都是 0**。

冷启动（进入一片从没缓存过的区域、要把首屏补齐）：1px=1 约 **0.8 秒**，1px=4 约 1.8 秒。
这期间地图会从中心往外长出来，不是干等。

### ⚠️ 真正的天花板在 Xaero 那边，不在这个程序

从 `XaerosWorldMap_1.37.6_Fabric_1.20.4.jar` 里反汇编出：

```
xaero/map/file/MapSaveLoad.class
    public static final int SAVE_TIME = 60000;      ← 硬编码，编译期常量
```

**Xaero 把地图写进 zip 是 60 秒一次的节流**，而且实测它的写入队列大约 **23 秒才落一个
region**（一个 region 只有 512 方块宽，鞘翅 33m/s 只要 15.5 秒就飞过去了）。
所以磁盘上的地图数据**天生滞后于你**，这是读 zip 这条路的物理上限，改配置也没用
（`SAVE_TIME` 是 `static final`）。

本程序能做的是**不让这个滞后被放大**：预取覆盖整屏、按距离排队、切档不重算。
要彻底消除滞后，只能不走文件——让模组直接从游戏内存读区块数据（见文末）。

### 为什么没有靠多线程加速解析

实测（8 片 region，纯 Python 解析）：

| 方式 | 耗时 | 加速比 |
|---|---|---|
| 串行 | 625 ms | 1.00x |
| 线程池 4 worker | 601 ms | 1.04x |
| 线程池 8 worker | 663 ms | **0.94x** |
| 进程池 6 worker | 824 ms | **0.76x** |

region 解析是纯 Python 循环（每片 5 万次逐格解析），受 GIL 完全限制——**线程越多反而越慢**
（切换开销），本机环境进程池也没拿到并行。所以线程数定在 4、预取队列上限 8，靠
"提前量"而不是"蛮力"来保证跟得上。

| **右键拖右下角** | **自由拖拽缩放**（右下角有小折角提示） |
| 滚轮上滚 / `z` | **放大地图**（同 Xaero） |
| 滚轮下滚 / `x` | **缩小地图** |
| `t` | 置顶开关 |
| `f` | 无边框开关（调试时想看标题栏） |
| `g` | 128 格网格开关 |
| `c` | 图层 auto → surface → cave 循环 |
| `m` | 地图源 auto（内存层+底图）→ mem（只用内存层）→ xaero（只用旧地图）循环 |
| `n` `p` | 手动切换维度+子图（切换后 `--dim` 锁定生效，再按 `c` 不会覆盖） |
| `v` | 坐标源 auto → bridge → ocr → manual → demo 循环 |
| `d` | Demo 巡游开关 |
| `r` | 遗迹提醒方式循环：`auto`（音+闪）→ `sound` → `both`（+抖动）→ `flag` → `off` |
| `h` | 帮助 |
| `Esc` / `q` | 退出 |

> **窗口缩放与地图缩放是两件事**，键位刻意分开：`+`/`-` 改的是**窗口多大**（视野随之变大），
> 滚轮改的是**地图比例**（每像素代表多少方块）。想同时用就 `Ctrl+滚轮` 缩窗口。
> 尺寸被夹在 `[160×120, 屏幕×98%]` 之间，拖不丢也拖不出屏。
> 实现上 Tk 无边框窗口改尺寸必须**同时**设 `canvas.configure(w,h)` 和 `root.geometry("WxH+x+y")`，
> 只改其一不生效。专项验证见 `_modtest/test_resize.py`。

## 遗迹标记

`scan_structures.py` 只能给出「异常方块聚集簇」——说明"这附近有东西"，认不出是哪一种。
所以：

```bat
python make_poi.py structures_DIM1.json --top 30 --min-count 500
```

会生成 `poi.json`，地图上显示为「候选遗迹 N块」菱形标记。
你人工确认后直接编辑 `poi.json` 把 `name` 改成真名（巫师/武士/白金…），或者手写新条目：

```json
[{"name": "巫师的修行所", "x": 1234, "z": -5678, "dim": "DIM1", "mw": "mw$default"}]
```

## 稀有遗迹提醒（巫师 / 武士 / 白金）

跑图时**新加载的区块里一旦出现这三类末地稀有遗迹，立刻提醒**。默认三种信号同时上：
**水滴音（连响三下）+ 闪烁任务栏 + 地图永久打点**；窗口抖动默认**关闭**，要用 `--ruin-alert both` 打开。

### 为什么"提醒方式"选这一套

需求给的是「水滴音」或「屏幕抖动」二选一。结论是**以水滴音为主通道，抖动改成抖地图窗口**：

| 通道 | 保留 | 理由 |
|---|---|---|
| **水滴音** | ✅ 主通道 | 骑鞘翅时眼睛盯的是**全屏游戏画面**，第二屏的地图只是余光。**只有声音是 100% 有效**的：不看地图也能听见。三种遗迹用**三个音高**，光听声音就知道是哪一种。 |
| **屏幕抖动** | ⚠️ 改成"抖动地图窗口" | 抖动**整个屏幕**需要注入游戏进程或改显示设置——Python 层没有正当手段做，硬做也会干扰操作。改成抖地图窗口：醒目、零侵入，而且和地图的视觉指向一致（声音把你叫过来，抖动告诉你"看这里"）。用 Tk `after` 链驱动，不阻塞主循环。 |
| **任务栏闪烁** | ✅ 补充 | `FlashWindowEx` + `FLASHW_TIMERNOFG`：**不抢焦点、不打断游戏**，切回桌面时能立刻看到是哪个窗口在报警。 |
| **地图打点** | ✅ 补充 | 图标+名字永久留在图上，事后可回看。 |

音效是**现场合成**的（`alerts.py` 里现算 WAV，不依赖任何外部音频文件）：
水滴声的物理来源是气泡振荡，频率**上滑**（不是下滑——下滑的正弦听起来像敲门/报警，不像水），
配指数衰减包络 + 一点二次谐波。三个音高分别对应三类遗迹。

### 为什么"新落盘的区块"就等于"新加载的区块"

模组只在**玩家真正加载了**的区块上写 `.bin` 文件。所以「文件是新出现的」天然等价于
「这块地形刚进视距」——正好是需求要的语义，而且**天然合规**：

- 只读模组已经落盘的数据，**绝不扫视距外**、不做任何自动化操作；
- 不需要额外的内存开销、不需要改模组、不需要扫地下。

另一个好处是**开销只跟玩家实际跑了多少成正比**：`RuinWatcher` 只处理
`index_<维度>.json` 里 **region 版本号变大**的目录，所以已经探索过的地图面积再大也不影响每轮耗时。

### 提醒通道：为什么以「声音」为绝对主通道

使用场景是**笔记本自带屏挂机飞末地跑图、外接大屏幕刷视频**——眼睛在外接屏上。
所以地图窗口、任务栏、游戏画面**全都在不被看的那块屏上**：

| 通道 | 是否默认开 | 理由 |
|---|---|---|
| **水滴音（连响三下）** | ✅ | **唯一 100% 有效的通道**。峰值归一化到满刻度 + 三连响，目的就是从视频声里穿出来 |
| 任务栏闪烁 | ✅ | 零成本（`FlashWindowEx`，不抢焦点）；切回桌面时能立刻看到是哪个窗口在报警 |
| 地图永久打点 | ✅ | 事后可回看，图标 `★/▲/◆` 区分类型 |
| 窗口抖动 | ❌（`--ruin-alert both` 打开） | 抖的是地图窗口，在**不看的那块屏**上，没用；开着还会和拖动窗口打架 |

三种遗迹用**三个音高**（白金高 / 巫师中 / 武士低），光听声音就知道是哪一种。
音效是**现场合成**的，不依赖任何外部音频文件。

### 识别算法：地块指纹（3 类，零类型混淆）

`structures_DIM1.json` 是对末地 1484 个 region 全量扫描出的 **1274 个人造结构候选簇**。
对其中三类取真实实例做统计，每类的特征方块一致率 100%：

| 遗迹 | 硬特征 (`anchors`，窗口内计数) | 并列通路（`any`，满足任意一组即可） |
|---|---|---|
| **白金星殿** | 虫蛀石砖 ≥35、红羊毛 ≥3 | ① `%@stone_brick` ≥0.30；② `@stone_brick` ≥120 且 `@mossy` ≥18；③ `@stone_brick` ≥120 且 平滑石台阶≥10 且 平滑石英楼梯≥10 |
| **武士的修行地** | `@end_brick` ≥30 | ① `@samurai_core` ≥90；② `%netherrack` ≥0.12；③ 下界岩≥60 且 磨制玄武岩≥8 且 `@crimson` ≥25 |
| **巫师的圣修所** | 磨制黑石砖 ≥100 | ① `%polished_blackstone_bricks` ≥0.26；② 裂纹磨制黑石砖≥30 且 黑石≥55 且 深板岩砖≥18 |

判据四条同时满足：① `anchors` 硬特征全部达标；② `ratios` 占比达标（若有）；
③ `any` 组**至少满足一组**；④ **纯度** = 本类特征方块 / 窗口内全部人造方块 ≥ 0.80。

> **为什么要有「占比锚点」（`ratios` / `any` 里的 `%键`）**：本服遗迹**直接刷新在地形上**，
> 有概率被地形方块覆盖。被淹没的列，其地表方块变成 `end_stone`（属自然方块，不计入统计），
> 于是**整座建筑的全部用料计数被等比缩小** s 倍（s = 露出比例）。由此：
> **纯度不变、占比不变，只有绝对计数会 × s**。所以凡是以**绝对计数**为锚点的判据，
> 淹没到一定程度**必然漏**——这是判据形式的缺陷，调阈值救不回来。
> 占比是**尺度无关**的，正好补这个洞；实测巫师淹没 70% 时新判据仍保 18/20，
> 旧判据淹没 50% 就归零了。

> **为什么 `any` 组要写成「占比 **或** 次要特征齐备」两条通路**：单用占比会漏掉
> 「完整露出但配料比例不同」的大实例（真机实测：`pbrick=493` 的完整巫师占比只有 0.245，
> 会被 0.26 卡掉）。两条通路谁满足都行，才能**同时**兼容这两种情况。

> **为什么硬特征必须写成「家族合计」（`@名字`）**：模组的每个 chunk 只存「**每列的
> 地表方块**」。同一座建筑换一个实例，露在地表的**家族成员会置换**。真机 4 个武士实例的
> 「末地石砖系」总量稳定在 64~67，但拆开看是 `end_stone_bricks` 15 + `end_stone_brick_wall`
> 38 + `end_stone_brick_stairs` 11；旧指纹把阈值钉在 `end_stone_bricks >= 90`（那个数字来自
> 另一个变体）上，于是**这 4 个实例全被漏掉**——这就是用户报的"旁边的武士遗迹没检测出来"。
> 同样的问题还有 `polished_basalt`：有个实例只有 11（旧阈值 20）。
> **把阈值钉在单个方块名上，等于赌"所有实例都露同一块砖"。**
>
> 家族定义写在 `ruins.json` 的 `groups` 里（`end_brick` / `stone_brick` / `mossy` / `crimson`），
> 只能出现在家族里的方块会自动并进该类型的纯度集合，改了 `groups` 不会忘记同步 `blocks`。
>
> **为什么要 `any` 组**：同上，只是这次换的是"整组材料"而不是"家族内成员"。
> 实测一处分金星殿只用 `mossy_cobblestone_stairs`（92），另一处只用
> `mossy_stone_brick_stairs`（22），固定阈值会把后者漏掉。
>
> **为什么还要纯度**：末地有上百个共用下界岩/黑石的小遗迹，光看"出现了哪些方块"会误伤。
> 纯度把它们和真遗迹分开。

> **武士为什么额外加一条「恒定构件合计」通路（`@samurai_core` ≥90）**：武士的用料分成两半——
> **恒定构件**（末地石砖系 / 净下界砖系 / 诡异台阶 / 绯红系，共 16 项，写进 `groups.samurai_core`）
> 每次完整露出，合计稳定在 **116~197**；**可变构件**（下界岩 5~200、磨制玄武岩 0~68）会被地形
> **整个埋掉**，实测有两座武士的 `netherrack` 只有 9~10、`polished_basalt` **归零**。
> 旧指纹把 `polished_basalt ≥5` 钉在 `anchors` 上 → 这两座**必漏**（这正是用户报的"两个武士没检测到"）。
> 更关键的是分离度：`@samurai_core` 第 17 名 = 116、第 18 名骤降到 66，其余**所有**建筑最大只有 66，
> 阈值 90 站在一条很宽的间隔带上。
>
> **这条通路必须用「绝对数」而不是「占比」**（注意与上面淹没段的结论相反）：被埋掉的只是低处的
> 可变构件，恒定构件在高处几乎不缩水（17 座实例全是 116~197 的满配），所以绝对数就是稳的；
> 实测改用占比反而更差（武士 0.36~0.80，其它建筑里也有 0.66~1.14 的，分不开）。
> **改指纹表时别"顺手"把 `samurai_core` 改成 `%@samurai_core`。**
>
> 另外 `samurai_core` **刻意不含** `end_stone_bricks`、也不含任何菌岩（nylium）：紫珀殿有大量
> `end_stone_bricks`、幽匿殿 `end_stone_bricks` 66 + `warped_slab` 16，放进去会互相串类。
> `dirt` 则要并进武士的 `blocks`（每座都有 18~33 列、且都在地形之上，是建筑自带的土质演武场，
> 不放进去纯度会虚低到 0.79 而漏检）。

**指纹表是可编辑的**：`app/ruins.json`（窗口大小、纯度阈值、`groups` 家族、每类的用料表/阈值/图标/颜色/音效）。

### 开局不会"炸响"，但会补报「以前漏掉过的」

启动时先做一次**基线扫描**（后台线程，实测约 20~35 秒 / 2.9 万个区块）。规则：

1. **已经在本机历史库**（`out/found_ruins.json`）里的遗迹 → **完全静默**（地图上照常打点）。
   理由：开局时地图上早就有那些遗迹了，一启动就把十几处全响一遍既不合语义也很吵。
2. **历史库里没有的**（= 这台机器从没报过，例如修好判据前漏掉的那些）→
   **合并成一条提醒，只报一次**，之后就进历史库不再响。

第 2 条是特意加的：用户的目标是"别因为看视频错过重要遗迹"，判据修好后第一次重启，
应该把"以前漏掉的武士"告诉他，而不是默默标到地图上。实测：基线正好找出那 6 处此前漏掉的
武士 → 响一声（`drop_low`，武士的音高）→ 再 tick 不再响。

之后每 0.6 秒扫一轮，**只有新落盘（region 版本号变大）的区块**才会触发提醒。
换局（`sid` 变化）时**不重扫**——模组的版本号会重排，按"变了就重扫"处理会让主线程卡十几秒，
这里直接把当前版本号当新基线，内存直方图保留（旧区块文件还在磁盘上，数据依然有效，
留着才能让判定窗口完整）。

命中记录落盘在 `app/out/found_ruins.json`（去重 96 格、保留 3 天），
提醒流水在 `app/out/ruin_alerts.log`（每行都写明**本次实际生效了哪些通道**，
以及没生效的通道名——见下面"提醒全都没生效"那条排错）。

### 维度消歧（把遗迹投到正确的图上）

本服有 20+ 个 `dimensionTypeId` 都是 `minecraft:the_end` 的目录（hard/easy/训练场…），
投点挂到错的图上就没意义了。按**可信度**从高到低：

1. **用模组自己的 region 坐标去比对**（置信度 2）：`index` 里记着它扫过哪些 region
   （与世界方块坐标系一致），哪个 Xaero 图里真的存在这些 region，哪个就是同一个世界。
   实测本机 `DIM1` 与模组 239 个 region 里重合 **235** 个，其余三个候选全是 **0** —— 结论唯一。
   这条**不需要游戏在线**。
2. `dim_map`：用玩家坐标算出来的映射（置信度 1）。
3. 按维度类型名解析（置信度 0）。

> **缓存必须带可信度**。地图每帧都会问一次，而**基线扫描完成前** `ruins.dims` 还是空的，
> 那时只能给出低可信度答案；如果就这么缓存住，等精确答案可用了也换不回来
> （实测：先缓存了 `minecraft$easy_the_end`，遗迹 POI 被全部过滤掉，**一个点都不显示**）。
> 现在只有"可信度升高"时才覆盖缓存。

## 内存直读层：怎么消掉滞后（已实现）

读 zip 的天花板是 Xaero 的 60 秒落盘节流，靠优化本程序绕不过去。根治办法是**不走文件**：
`coordbridge` 模组直接从**游戏内存**里读玩家周围已加载的区块，落盘给跟随地图用。

### 取值链路（全部纯反射，不链接任何 MC 类）

```
Minecraft.getInstance().level                        (ClientLevel)
  .getChunkSource()                                  (ClientChunkCache)
  .storage                                           (Storage)
  .chunks          (AtomicReferenceArray，JDK 公开类，可直接强转调用)
  -> LevelChunk
     .getPos()                          -> cx / cz
     .getHeight(WORLD_SURFACE, x, z)    <- 每列 1 次，直接拿到地表高度
     .getSections()[i].getBlockState(x, y&15, z)
     -> BlockState.getBlock() -> BuiltInRegistries.BLOCK.getKey(block) -> "minecraft:grass_block"
```

**为什么用 heightmap 而不是从 y=15 逐层往下扫**：一个 section 有 4096 个方块，
"逐层找每列第一个非空气"最坏要几万次反射调用；而客户端 chunk 自带 `WORLD_SURFACE`
heightmap，每列 1 次调用拿到高度、再 1 次取方块名，**每 chunk 固定约 512 次调用，
且耗时不随地形起伏变化**。拿不到 heightmap 时自动退化为逐段扫描。

**为什么能直接强转 `AtomicReferenceArray`**：它在 `java.base` 的**导出包**里，
调它的 public 方法（`length()` / `get(int)`）不需要 `setAccessible`，因此不会撞上
JDK 强封装（`InaccessibleObjectException`）。反过来说，用 `java.lang.reflect.Array`
去读它反而会炸 —— 这是这个方案能成立的关键细节。

反射名全部由 `modmap.py` 从「Mojang 官方映射 + Fabric intermediary」确定性推导，
固化在 `Names.java` 里；改过映射表要重跑 `python modmap.py` 核对。

### 扫描怎么排优先级（跑图跟得上的关键）

单次反射调用约 0.1~0.3µs，视距内几百个 chunk 全扫一遍是十万次的量级。扫描器每轮：

1. **枚举**所有已加载 chunk 的坐标（只读坐标，几百次调用，开销可忽略）；
2. 按「**多久没扫过** → **离玩家多远**」排序；
3. 处理到**时间片用完**（默认 60ms）为止，然后 sleep 90ms。

这样同时拿到两个保证：

- **脚下的地形永远最新** —— 玩家周围的区块每一轮都会被排到最前面；
- **远处的区块不会饿死** —— 排序的第一关键字是"多久没扫过"，所以最久没被碰过的
  区块一定会优先被处理，不会出现"永远只扫身边一圈"的情况。

按距离排序而不是按数组下标轮转，是因为 `Storage.chunks` 的下标是 chunk 坐标的哈希，
**没有空间局部性**：按下标轮转时，新进入视距的区块可能排在很后面，要等整轮才被扫到。
排序后新区块（`since` 取上限）必然排在最前。

实测本机单 chunk 约 0.08ms（16×16 列 ×2 次反射调用），视距内 ~600 个 chunk 一整轮
约 50ms —— 也就是**每 150ms 左右全量刷新一遍**。鞘翅 33m/s 时这段时间只飞 5 格。

可调：`-Dcoordbridge.slice=80 -Dcoordbridge.sleep=60 -Dcoordbridge.budget=2048`。

### ★ 踩过的坑：映射写错 → 模组「静默失效」

这是本项目最坑的一个 bug，强烈建议保留这段记录：

早期 `modmap.py` 解析方法时**只按「类 + 方法名」匹配，忽略描述符**。obf 名会被
压成 `a`/`b`/`c`，一个类里同名的重载极多 —— `LevelChunkSection.getBlockState`
就有 6 个 obf 名都叫 `a` 的重载。于是解析出来的是同名的 `()V` 方法：

| 键 | 错的值 | 正确的值 |
|---|---|---|
| `M_SEC_BLOCK` | `method_16676` `()V` | **`method_12254`** `(III)LBlockState;` |
| `M_GET_HEIGHT` | `method_12040` | **`method_12005`** |
| `M_REG_KEY` | `method_40264` | **`method_10221`** |

**表现极具误导性**：反射在运行时抛 `NoSuchMethodException`，但这个异常被
`round()` 的 `catch (Throwable)` 吞掉了 —— 游戏不崩、聊天栏没提示、日志没有异常，
模组只是**永远不写任何数据**。从外面看就是「地图更新一直跟不上」，
看起来像性能问题，实际是内存层从头到尾就没工作过，一路在用 60 秒落盘的 Xaero。

**两道防线（现在都有了）**：

1. **解析端**：`mapbridge.Bridge.method()` 现在把「源码风格描述符」转成 obf JVM
   描述符，去 intermediary 映射里按 `(类, 描述符, 方法名)` **精确三元组**取名字；
   命中不唯一直接报错。`python modmap.py --check` 逐字核对 `Names.java`。
2. **运行端**：解析出的 `Method` 描述符必须与 `Names.sigs()` 里的预期值**逐字相同**，
   否则判定为失败。`~/.coordbridge/scan_status.txt` 里会直接写出：

   ```
   state        : FAIL IllegalStateException: 找不到 LevelChunkSection.getBlockState
     [miss] method_16676 argc=3 in net.minecraft.class_2826
   ```

   手头没有游戏时也能提前发现：`diagnose.py` 第 7 步会读这段并直接报 FAIL + 修法。

### 怎么在**没有游戏**的情况下验证（_modtest/）

模组全程只用字符串 + `Class.forName`，不链接任何 Minecraft 类 —— 所以只要提供一批
**类名 / 字段名 / 方法名 / 描述符完全一致**的桩类，就能在纯离线环境里把整条链路跑通：

```bash
python _modtest/gen_stubs.py --run     # 生成桩类 -> 编译 -> 跑 -> 校验
python _modtest/test_modref.py         # 编好的 jar：纯反射？常量表各版本一致？版本谓词范围对？
python _modtest/bench_mem.py           # 合成末地数据，实测 Python 侧渲染耗时
python _modtest/probe_latency.py       # 地图延迟分段探针（真机数据 + 端到端）
```

`gen_stubs.py` 会造一个 4×4 chunk、地表 y=63 全石头的假世界，启动**真实的
`ChunkScanner`**，再把落盘的 `.bin` 交给 Python 侧 `parse_chunk` 读回比对。
它同时是一个回归测试：把 `Names.java` 里任一名字改错，输出里就会出现
`[miss] ...` 且 `REF_OK=false`（已实测）。

它还会**双向核对桩类与 `Names.java` 是否同步**：桩类里写死的名字一旦与映射脱节，
这套离线验证就从"证明"退化成"自证"——表面一路 OK，实则什么都没覆盖。所以
正向查「`Names.java` 每个常量都在桩源码里出现过」，反向查「每个桩 `class_xxx`
都被 `Names.java` 引用」。`test_modref.py` 则直接解析 jar 的 class 常量池，
确认里面**没有** `net.minecraft.*` 的 `CONSTANT_Class` 项（真正链接 MC 类的标志），
并把 `fabric.mod.json` 的版本谓词交给**真实的 fabric-loader** 去解析验证。

### 落盘格式（小端，每 chunk 一个文件）

```
u32 magic 'CBB1' | u16 ver | u16 flags | i32 cx | i32 cz
u16 palCount | palCount × (u16 len + UTF-8 方块名)
256 × i16  colY    (该列地表方块的世界 y；-32768 = 无数据)
256 × u16  colIdx  (调色板下标；0xFFFF = 无数据)        顺序均为 z*16+x
```

路径 `~/.coordbridge/chunks/<维度>/r<rx>/r<rz>/<cx>_<cz>.bin`，按 region 分两级子目录
（一个维度跑久了会有上万个文件，平铺在一个目录里会让外部 `listdir` 变慢）。
另有 `index_<维度>.json`：

```json
{"dim":"minecraft:the_end","sid":1791466955646,"rev":7,"t":...,"chunks":612,
 "regions":{"0,0":7,"1,-1":3}}
```

- `regions` 给出每个 region 的版本号 —— Python 侧据此判断哪块需要重建；
- `sid` 是**本局游戏**的会话号。region 版本号每局都从 1 重新计数，缓存键不带 `sid`
  的话，重开游戏就会命中上一局留下的同号缓存、显示旧地形。所以内存缓存、磁盘
  PNG 缓存的名字里都带 `sid`。

### Python 侧：为什么重建一个 region 只要几毫秒

实测本机（Windows）**单次 `stat` 约 170µs、单次 `open` 约 180µs** —— 这是整条链路上
最贵的东西，比 Python 逻辑本身贵两个数量级。一个满铺 region 有 1024 个文件，
"每次重建都 stat + 读一遍"就是 350ms，一屏几十个 region 直接卡死。

所以做了三件事：

1. **逐 chunk 增量缓存**：`MemLayer` 为每个 chunk 缓存
   `(mtime_ns, rgba16×16, mask16×16)`，重建 region 时只有 mtime 变了的文件才重新解析。
   模组本身也只重写内容变了的 chunk，所以稳态下每轮只有个位数文件需要读。
2. **用 `DirEntry.stat()` 而不是 `os.stat(path)`**：`os.scandir` 在 Windows 上通过
   `FindNextFileW` 已经把 `WIN32_FIND_DATA`（含 mtime）拿到了，`DirEntry.stat()`
   直接用缓存，**不产生额外系统调用**。单这一步就把 256 次 stat 的 44ms 变成 ~0。
3. **UI 线程永不构建**：`CompositeStore.get(..., allow_build=False)` 时内存层只查缓存，
   缺的那张丢给后台线程池（`MemLayer.request`），这一帧先显示 Xaero 底图，下一帧
   内存层自然出现。`region_image(allow_build=False)` 会直接返回 None 而不是开建。
   **例外**是「热重建」——见下面第 4 条。

4. **热 region 就地重建**（2026-10-11 新增）：上面那条规则对**冷建**是对的（1024 chunk
   的 region 冷建实测 420ms，放进 UI 线程就是卡帧），但**热**重建（这个 region 之前建过、
   逐 chunk 小块还在 `_ccache` 里）只要 **40~50ms**。这种就**当帧直接做完**，数据当帧出现，
   省掉「丢后台 → 下一帧才画」的整整一帧。用令牌桶限速（每秒最多 5 片、最多攒 2 片），
   保证玩家狂奔时也不会把帧时间堆起来；`--no-inline` 可关。

实测（`_modtest/bench_mem.py`，256 chunk/region）：

| 场景 | 优化前 | 优化后 |
|---|---|---|
| 冷建一个 region | 172 ms | 57 ms |
| 热重建（1 个 chunk 变化） | 52 ms | **6.5 ms**（`_build` 内部） |
| 整屏 9 个 region 冷建 | 1282 ms | 435 ms |
| 整屏 9 个 region 缓存命中 | — | **0.15 ms** |
| 视口合成一帧（含裁剪/POI/HUD） | — | 1.7 ms |

## 地图延迟：瓶颈在哪、怎么压

> 需求原话：「给出可以压低地图延迟的方案」。

延迟 = **数据新鲜度**（模组写盘 → Python 看见） + **帧周期**（每帧做多少事 + `--interval`）。
用 `python _modtest/probe_latency.py` 逐段实测（真机数据 + 合成端到端），结论如下。

### 最大的坑：每帧重扫上百个目录（已修）

`app._resolve_xaero()` 每帧都要问一次「玩家现在在哪张子图」，它调
`DimResolver.candidates(fix.dim)`。而这个函数**没有任何缓存**，每调一次就对**所有**
候选目录做一轮 `os.listdir` + 逐文件 `getmtime`：

| 调用 | 单次耗时 | 说明 |
|---|---|---|
| `candidates(minecraft:overworld)` | **316 ms** | 103 个候选目录 |
| `candidates(minecraft:the_end)` | **211 ms** | 4 个候选目录（但每个目录 zip 极多） |
| `app.step()` 整帧 | **310 ms** | 其中 `candidates` 占 270ms = **91%** |
| 真正画地图（`MapView.render`） | 7.7 ms | — |

也就是说：**每帧 310ms 里有 270ms 花在反复列目录上，只有 7.7ms 在画图**，帧率被压到
**1.8 fps**（`--interval 250` 时帧周期 560ms）。

> ⚠️ 注意 `--selftest` 用的是 `--source demo`，`fix.dim` 是空的，**恰好绕过这条路径**
> —— 自检里是 11 fps，看着很正常。真机跑 bridge 才暴露出来。

修法：`TileStore.scan_dir()` 用**一次 `os.scandir`** 同时拿到「region 坐标集合」与
「最新 mtime」（`DirEntry.stat()` 走 Win32 目录枚举自带的数据，不额外产生系统调用），
带 TTL 缓存；`_existing()` / `last_activity()` / `_pairs()` / `build_dim_map()` 全部复用它；
`DimResolver.candidates()` 再加一层 2 秒结果缓存（Xaero 自己 60 秒才落一次盘，2 秒缓存
不会看漏任何东西）。`dims()` 也加了 5 秒缓存（一次要 42ms，有三处会调它）。

### 改前改后（真机 bridge 路径插桩，40 帧）

| 指标 | 改前 | 改后 |
|---|---|---|
| `app.step()` 每帧（中位） | **310 ms** | **1.8 ms** |
| `resolver.candidates()` | 270 ms/帧 | 2.2 ms/帧（绝大多数命中缓存，≈0.001ms） |
| `_pairs()`（原每 15s 一次 366ms 卡顿） | 366 ms | 60s 一次 ~56ms，且改用一次扫描 |
| `TileStore.dims()` | 57 ms | 5 秒缓存 → ≈0 |
| HUD 文字渲染 4 行 | 5.1 ms | **0.002 ms**（加了 LRU 缓存） |
| 每帧固定开销合计 | 19.6 ms | **7.8 ms** |
| 帧周期（`--interval 250`） | 560 ms / 1.8 fps | 128 ms / 7.8 fps |

### 数据新鲜度：`MemLayer._index` 的 TTL

`index_<维度>.json` 里记着每个 region 的版本号，Python 靠它判断「这块地形变了没有」。
原先是 1.0 秒硬 TTL —— 等于白送 1 秒延迟。改成 **mtime 门控**：每帧只多一次
`os.stat`（~0.17ms），文件没变就不重新解析 JSON，一旦模组重写就立刻重读。

顺带加了一条防御：模组是**直接覆写**这个文件的，TTL 一短就更容易读到写了一半的内容
（截断 JSON → `ValueError`）。这时必须**沿用上一次读到的值**，否则会把内存层误判成
「该维度无数据」，整屏退回滞后的 Xaero 底图。

### 端到端结果（合成数据、走真实代码路径）

`_modtest/probe_latency.py` 会造一份最小内存层数据，照主程序每帧的做法轮询，
然后改写一个 chunk，量到画面像素真的变了为止：

| 帧周期 | 改前 | 改后 |
|---|---|---|
| `--interval 250` | 506 ms | **257 ms** |
| `--interval 120`（新默认） | — | **127 ms** |

所以默认 `--interval` 从 250 收到 **120**（渲染一帧只要 ~8ms，调小很划算）。

### 还剩哪些可以再压（按收益/风险排序）

| # | 方案 | 预估收益 | 代价/风险 |
|---|---|---|---|
| 1 | 模组 `SLEEP_MS` 90 → 40（`ChunkScanner`） | 源头全量刷一遍 ~90ms → ~45ms | 需重编 jar；扫描线程 CPU 翻倍，可能影响游戏帧率 |
| 2 | 内存层瓦片**不写磁盘**（只留内存 LRU） | 省掉每个版本一次 PNG 编码（后台 ~10~20ms） | 重启地图工具后不能复用同一局的缓存，要重新建一次 |
| 3 | `--interval` 再降到 60~80 | 端到端再降 ~40~60ms | 更耗 CPU；笔记本挂机更费电 |
| 4 | Xaero 底图也做「就地热重建」 | 底图刷新少一帧 | 底图 60 秒才落盘一次，收益很小 |
| 5 | 把 `_pairs()` 挪到后台线程 | 消掉每 60 秒一次的 ~56ms 小卡顿 | 结构要改（多一个后台 job），收益不大 |

第 1 项是**源头**，但会动游戏内负载，建议先只在需要时用 `-Dcoordbridge.sleep=40`
（JVM 参数，不用重编）试，确认游戏帧率不受影响再固化。

### 安全性与已验证范围

只读、不写游戏状态、不发任何网络包。后台线程读 chunk 是安全的：`chunks` 是
`AtomicReferenceArray`（读引用原子），而 `LevelChunkSection` 在客户端收包时是**整体替换**
而不是原地改写，所以最多读到一份"略旧但自洽"的数据，不会读到半更新状态。

**已经端到端验证过**：

- **离线桩类全链路**（`_modtest/gen_stubs.py --run`）：反射解析 → heightmap 取值 →
  `getBlockState` → 方块名 → 二进制落盘 → Python 侧 `parse_chunk` 读回，逐项核对通过；
  故意把 `Names.java` 改错时会被描述符自检拦住（`[miss]` + `REF_OK=false`）。
- **多版本通用**（`_modtest/test_modref.py`，12 项全过）：解析 jar 的 class 常量池确认
  **没有任何 `net.minecraft.*` 的 `CONSTANT_Class` 项**（只链接 `net.fabricmc.api.ClientModInitializer`），
  且 MC 类名以字符串常量形式存在；逐项比对 1.20.1/1.20.2/1.20.3/1.20.4 的常量表（63 项全同）；
  并把 `fabric.mod.json` 的 `>=1.20.1 <1.20.5` 交给**真实的 fabric-loader**（0.14.22 / 0.16.13 /
  0.16.14 三个版本各验一遍）确认接受 1.20.1~1.20.4、拒绝 1.20.5 与 1.21。
- **负样本**：不存在的 chunk / 全空气 chunk 正确跳过；内容 hash 未变时不重复写盘。
- 二进制解析往返、调色板、chunk→region 坐标映射、着色结果与 Xaero 通道**逐像素一致**；
  合成后「有内存数据的 region 与 Xaero 一致」「没有内存数据的 region 完整保留底图」；
  主程序在有内存数据时自动切到 `$mem`。
- **1.20.1 的 Xaero 数据也能解析**：拿本机 1.20.1 实例里 1264 个真实 region 抽样 40 个，
  `strict=True`（要求恰好消费完整个文件）**40/40 通过**，格式版本 `(6,7)`；1.20.4 的是 `(6,8)`。
  解析器本来就按文件头里的 `minor` 分档，两种都覆盖。

**模组已在运行中的 1.20.4 游戏里长期实跑**（`~/.coordbridge/` 的数据持续在涨，
末地已 5 万+ chunk / 165 region）。**改过 jar 必须重启游戏**才会生效。看 `~/.coordbridge/scan_status.txt`：

```
heightmap    : OK
mode         : heightmap
loaded chunks: 613
last round   : scanned 438 chunks, written 214, 58 ms
full sweep   : 约 82 ms（越短越跟得上跑图）
total written: 2145
state        : OK
  [ok] method_12254 (III)Lnet/minecraft/class_2680;  <- net.minecraft.class_2826
  ...
```

`state : OK` + `[ok]` 若干行 + `full sweep` 在百毫秒级 = 内存层真正在跟着跑图。
若出现 `state : FAIL` / `[miss]`，跑 `python diagnose.py`，第 7 步会直接给出修法。
